# MAVLink2 Investigation Summary (2026-01-12)

## Scope
- QGC fork: `c:\Hien\ALES_QGC_argos`
- FC firmware: `c:\Hien\APM4.0`
- Middleware: `c:\Hien\AB-120-P120501\AB-120`

## Symptoms
- QGC log: "Need mavlink2 for item transfer" during mission/fence/rally load.
- PlanManager logs: `Incorrect mission_type received expected:actual` with expected 1/2 but actual 0.
- Raw frames show QGC sending MAVLink2 (STX `FD`) while FC replies with MAVLink1 (mission_type defaults to 0).

## QGC Code Updates (ALES_QGC_argos)
- Forced MAVLink2 in `MAVLinkProtocol::setVersion` (clamps to `>= 200`).
- Added logging for TX/RX mission-related MAVLink messages:
  - `src/Vehicle/Vehicle.cc` (TX, raw hex, only mission msgids)
  - `src/comm/MAVLinkProtocol.cc` (RX, raw hex, only mission msgids)
  - Logs use `qInfo` to reduce spam.
- Added MAVLink2 signing setup sender on first heartbeat per channel:
  - `src/comm/MAVLinkProtocol.cc` sends `SETUP_SIGNING` to target sysid/compid.
  - Hardcoded signing key (32 bytes, hex):
    `e47ad8f8d4407a84bfcc8ba5b29ec7a286d611de5bde85cf998dae3e87c1ad4b`
  - Tracks per-channel send in `MAVLinkProtocol.h` using `QSet<int>`.

## APM4.0 Findings
- `libraries/GCS_MAVLink/GCS_Common.cpp`:
  - If signing is not enabled, FC starts output as MAVLink1 even when protocol is MAVLink2.
  - `MAVLINK_COMM_0` always starts MAVLink1 (recovery behavior).
- `libraries/GCS_MAVLink/GCS_Signing.cpp`:
  - Signing key stored in FRAM; enabled via MAVLink `SETUP_SIGNING` message.
  - No parameter for signing key; it must be set by GCS.
- `libraries/AP_SerialManager/AP_SerialManager.cpp`:
  - `SERIALx_PROTOCOL` defaults: port 0 = MAVLink2, port 1 = MAVLink (v1). Must be configured explicitly per port.

## AB-120 Middleware Findings
- `argosLinker/MAVProxy/MAVProxy.cpp`:
  - UDP -> FC and FC -> UDP are forwarded as raw MAVLink; no version translation for mission/fence.
  - MAVLink1 <-> MAVLink2 conversion exists only for PARAM_EXT wrapper (custom msgid 204/205).
  - Therefore AB-120 does **not** force MAVLink1 for mission/fence; it simply forwards what it receives.

## Root Cause (Most Likely)
- FC is still outputting MAVLink1 on the active port (due to signing disabled and/or MAVLINK_COMM_0 behavior), so mission/fence/rally ACKs come back as MAVLink1 (mission_type=0). QGC expects MAVLink2 mission_type (1/2) and reports the error.

## Next Actions / Options
1) **Firmware-side**: make FC send MAVLink2 consistently.
   - Ensure correct `SERIALx_PROTOCOL=2` for the active telemetry port (not just port 1/2, verify actual physical port in use).
   - Consider disabling the ?always start MAVLink1 on MAVLINK_COMM_0? logic in `GCS_Common.cpp` if safe for your environment.
   - Enable MAVLink2 signing by accepting the `SETUP_SIGNING` key (now sent from QGC).

2) **QGC-side**: confirm `SETUP_SIGNING` is transmitted and FC accepts it.
   - Use QGC logs to verify TX of `SETUP_SIGNING` and FC responses.

3) **Middleware** (AB-120): optional verification only.
   - Add STX logging for mission messages to verify whether frames from FC are `0xFE` or `0xFD`.
