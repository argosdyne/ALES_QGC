# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ALES QGC ("Ales QGroundControl", binary `AlesQGroundControl`) is ARGOSDYNE's fork of QGroundControl 4.4, used as the ground control station for ARGOSDYNE UAS (AQUILA series, CUNA drone-in-a-box). Defects here can cause loss of aircraft control, so flight safety and correctness come before style. See `REVIEW.md` for the review rules (Important vs. Nit criteria, files to skip, things to always check).

- Working branch: `Argos_Stable4.4`. Release branches are named `ALES_QGC_VXX.YY.ZZ` and get merged back into it.
- **Toolchain: Qt 5.15.2 with qmake** (`qgroundcontrol.pro`). CI uses this too. `CMakeLists.txt` is upstream and not the build ARGOSDYNE uses. `REVIEW.md` says "Qt 6", but the code targets Qt 5.15.
- Commit and PR titles usually reference the internal tracker, e.g. `bug #9380 [AlesQGC] ...` or `task #9388 [ALES-QGC] ...`.

## Build

Submodules are required (`git submodule update --init --recursive`). They include mavlink `c_library_v2`, GpsDrivers, libevents, eigen and others. Use a shadow build directory.

Desktop (Linux and Windows CI, see `.github/workflows/*.yml`):
```
mkdir build && cd build
qmake -r ../qgroundcontrol.pro CONFIG+=debug     # or CONFIG+=release; Windows CI uses jom
make -j8
```

Android (from README; JDK 11, NDK 21.3.6528147, Qt 5.15.2 android kit, with env vars JAVA_HOME / ANDROID_NDK_ROOT / ANDROID_SDK_ROOT set):
```
qmake.exe ../qgroundcontrol.pro -spec android-clang "CONFIG+=debug" "CONFIG+=qml_debug" ANDROID_ABIS="arm64-v8a"
%ANDROID_NDK_ROOT%\prebuilt\windows-x86_64\bin\make.exe -j8
%ANDROID_NDK_ROOT%\prebuilt\windows-x86_64\bin\make.exe apk
```

The `custom/` plugin is picked up automatically when the directory exists (`qgroundcontrol.pro` includes `custom/custom.pri` unless `CONFIG+=QGC_DISABLE_CUSTOM_BUILD`). Local build options can go in an untracked `user_config.pri`.

## Tests

Unit tests are compiled only into debug builds (`UNITTEST_BUILD`, sources in `src/qgcunittest` and `*Test.cc` under `src/`). Run them through the app binary:
```
./staging/qgroundcontrol-start.sh --unittest            # Linux, all tests (CI wraps with xvfb-run -a)
<binary> --unittest:<TestClassName>                     # single test
```
CI copies `test/qtlogging.ini` to `~/.config/QtProject/` and sets `QT_FATAL_WARNINGS=1` before running them.

## Architecture

Upstream QGC structure: `QGCApplication` owns a `QGCToolbox` of singleton managers (LinkManager, MultiVehicleManager, SettingsManager, VideoManager, and so on). `Vehicle` holds per-vehicle state as `FactGroup`s. `FirmwarePlugin`/`AutoPilotPlugin` adapt behavior per autopilot. The QML UI (`src/ui`, `src/FlightDisplay`, `src/PlanView`, ...) binds to C++ through `QGroundControl.*` globals. Settings are declared in `*.SettingsGroup.json` metadata and backed by `SettingsGroup` subclasses.

ARGOSDYNE customization lives in two places:

1. **`custom/` (QGCCorePlugin custom build).** `custom/custom.pri` sets branding (app name, org, Android package `org.Agosdyne.alesqgc`), defines `CUSTOMCLASS=CustomPlugin` and `CUSTOMVEHICLECLASS=CustomVehicle`, and lists every custom source. When you add a file under `custom/src`, add it to `SOURCES`/`HEADERS` there. `CustomPlugin` (`custom/src/CustomPlugin.*`) exposes the ARGOSDYNE managers to QML as properties:
   - `CodevSettings` / `CustomSettings` (settings groups `Codev.SettingsGroup.json`, `Custom.SettingsGroup.json`)
   - `CodevRTCMManager` (RTCM/NTRIP and serial correction sources, `custom/src/RTCM`)
   - `SiYiManager` (SiYi camera/gimbal and transmitter over TCP, `custom/src/SiYi`)
   - `YSManager`, `ARLink` (`ARManager`/`ARConnection`), `AVIATORInterface`, `FlightZoneManager`
   - `CustomFirmwarePlugin(Factory)`, `CustomAutoPilotPlugin`, `CustomVehicle` and `VehicleESCFactGroup`

2. **Direct edits to upstream `src/`.** A large share of fork changes go straight into upstream directories, mainly `src/Camera` (e.g. `CodevCameraControl*`, changes to `QGCCameraControl`/`QGCCameraManager`), `src/MissionManager`, `src/Vehicle`, `src/QmlControls`, `src/PlanView`, `src/FlightDisplay` and `src/Settings`. Don't assume `src/` matches upstream QGC 4.4.

**QML/resource overriding:** `custom/qgroundcontrol.qrc` and `custom/qgcresources.qrc` replace the root `.qrc` files in the custom build. They are generated by `custom/updateqrc.py` (run it from `custom/`), which copies the root qrc files minus the entries listed in `custom/*.exclusion`. `custom/custom.qrc` then re-registers the same aliases pointing at custom files, e.g. `FlyViewVideo.qml` → `custom/CustomFlyViewVideo.qml` and `GPSIndicator.qml` → `custom/CustomGPSIndicator.qml`. When you edit an upstream QML file, first check whether an override in `custom/` shadows it. When you add a QML/resource file to a root `.qrc`, the custom qrc files must be regenerated or updated too, or the file is missing from the custom build.

For UI work (including implementing Figma designs), see `.claude/rules/figma-design-system.md`. It covers QGCPalette color tokens, ScreenTools sizing, component modules, assets and icons.

## Translations

Every `translations/qgc_*.ts` is compiled and embedded by qmake (`TRANSLATIONS` + `CONFIG+=lrelease embed_translations` in `qgroundcontrol.pro`). `QGCApplication.cc` loads two translators per locale from `:/i18n`:
- `qgc_source_<locale>.ts`: `tr()`/`qsTr()` strings from C++ and QML
- `qgc_json_<locale>.ts`: strings from `*.json` metadata (FactMetaData, MAVCmdInfo). The context is the JSON file name, and the keys come from `translateKeys`. See `translations/README.md`.

Source catalogs are regenerated with `translations/qgc-lupdate.sh` (`lupdate ../src` plus `qgc-lupdate-json.py`). Its `QT_PATH` is hard-coded for macOS.

To add a UI language:
1. Add the `.ts` pair.
2. Add the entry to `qLocaleLanguage` `enumStrings`/`enumValues` in `src/Settings/App.SettingsGroup.json`. The values are `QLocale::Language` numbers.
3. Add the language to `AppSettings::_rgReleaseLanguages` or `_rgPartialLanguages` (`src/Settings/AppSettings.cc`). Stable builds hide any language that is in neither list.

The whole `enumStrings` value is one translation key. Editing it changes the source string in every `qgc_json_*.ts`, so update all of them, or existing translations of the language list stop matching.

Vehicle status texts that contain values (e.g. "Compass 2 not calibrated") are translated in `src/uas/StatusTextTranslator`. It matches them against the printf-style `UASWarning` keys listed in `src/uas/UASWarningPatterns.h`. That header is generated: rerun `python3 tools/generate_uaswarning_patterns.py` (it reads `qgc_source_ko_KR.ts`) after adding `UASWarning` strings with placeholders.

## Versioning

The user-visible version is hard-coded in `QGroundControlQmlGlobal::qgcVersion()` (`src/QmlControls/QGroundControlQmlGlobal.cc`, e.g. `"V01.29.00"`). A version bump also updates the release branch name in the `push.branches` trigger of `.github/workflows/windows_release.yml`. `CUSTOM_QGC_VERSION` in `custom/custom.pri` is separate and not the displayed version.
